# 1. วิสัยทัศน์ของเกม

## 1.1 แนวเกม

เกม 3D Co-op Horror Comedy Multiplayer ที่ผู้เล่นร่วมมือกันไขปริศนา สำรวจพื้นที่ เก็บสิ่งของ ทำภารกิจ และเอาชีวิตรอดจากสิ่งเหนือธรรมชาติ

แรงบันดาลใจด้านประสบการณ์มาจาก R.E.P.O. และ Content Warning แต่ **ห้ามลอก** ต้องมีเอกลักษณ์ของตัวเองทั้งระบบเกม ปริศนา ผี สไตล์ภาพ อารมณ์ขัน และประสบการณ์เล่นร่วมกัน

เกมควรให้ความรู้สึก:

- เล่นกับเพื่อนแล้วเกิดเหตุการณ์ตลกที่คาดเดาไม่ได้
- ต้องช่วยกันคิดและสื่อสารเพื่อแก้ปริศนา
- ระทึกจากผีและเหตุการณ์ที่ไม่แน่นอน
- ความผิดพลาดกลายเป็นเรื่องฮาได้
- เล่นซ้ำได้โดยไม่จำเจเร็วเกินไป
- มีความก้าวหน้าให้อยากกลับมาเล่น
- ไม่ลงโทษหนักจนเครียดหรือหมดสนุก
- เล่นคนเดียวได้ โดยออกแบบสมดุลสำหรับ Solo โดยเฉพาะ ไม่ใช่แค่ลดจำนวนผู้เล่น

## 1.2 งบประมาณและเวลา

- ไม่มี Deadline ตายตัว ให้ความสำคัญกับคุณภาพ ความเสถียร และการออกแบบที่ดี
- แต่ต้องบริหารขอบเขตอย่างฉลาด: ระบบพื้นฐานเล่นได้ก่อน แล้วค่อยขยาย
- ห้ามสมมติว่าบริการออนไลน์ฟรีตลอดไป ต้องตรวจ Free Tier, โควตา, ค่าใช้จ่ายแฝง, การผูกบัตร และเงื่อนไขจริง
- ห้ามแนะนำบริการแบบเสียเงินโดยไม่แจ้งและขออนุญาตก่อน

## 1.3 ภาษาในเกม

- ภาษาเริ่มต้นคือภาษาไทย และเปลี่ยนเป็นภาษาอังกฤษได้จาก Settings
- ข้อความที่ผู้เล่นเห็นทั้งหมดต้องผ่านระบบ Localization ห้ามฝังข้อความในโค้ด
- ภาษาไทยต้องแสดงผลถูกต้อง: ฟอนต์, สระและวรรณยุกต์ไม่ซ้อนผิดตำแหน่ง, การตัดบรรทัด (ภาษาไทยไม่มีช่องว่างระหว่างคำ), การจัดวางบน UI
- **การแสดงผลภาษาไทยเป็นความเสี่ยงทางเทคนิค** ต้องทดลองให้ได้ผลตั้งแต่ Milestone 2 ไม่ใช่ไปเจอปัญหาตอนทำ UI

## 1.4 แพลตฟอร์มและการเผยแพร่

**แพลตฟอร์ม:** Windows 64-bit เท่านั้นในเวอร์ชันนี้

แม้ยังไม่ทำ macOS ให้รักษาความเป็นไปได้ในอนาคตด้วยต้นทุนต่ำ:

- หลีกเลี่ยง API หรือ Plugin ที่ใช้ได้เฉพาะ Windows เมื่อมีทางเลือกที่ Cross-platform
- ใช้ Path แบบ Unity (เช่น `Application.persistentDataPath`) ไม่ Hard-code Path ของ Windows
- ตอนเลือกบริการ Multiplayer และ Voice ให้บันทึกด้วยว่ารองรับ macOS หรือไม่ (ใช้เป็นข้อมูล ไม่ใช่เงื่อนไขบังคับ)
- ห้ามใช้เวลาทำงานเพื่อ macOS เพิ่มจนกว่าฉันจะสั่ง

**Repository และ Release:**

- ใช้ Repository เดียวสำหรับ Source Code
- ไฟล์เกมที่ Build แล้วอยู่ใน **GitHub Releases** เท่านั้น ห้าม Commit ไฟล์ Build, Cache, Library หรือไฟล์ชั่วคราว
- ตั้งชื่อไฟล์ Release ให้มีเวอร์ชันและแพลตฟอร์ม เช่น `<GameName>-v0.1.0-Windows.zip`
- เกมต้องตรวจเลขเวอร์ชันตอนเข้าห้อง ถ้าไม่ตรงกันให้แจ้งผู้เล่นอย่างชัดเจนว่าต้องอัปเดต
- Repo มี `.gitignore` และ `.gitattributes` (LFS) อยู่แล้ว ให้ตรวจว่าครอบคลุม `Builds/`, ไฟล์ `.blend` ใน `ArtSource/` และ Line Endings ของไฟล์ข้อความ แล้วปรับเท่าที่จำเป็น
- เกมจะไม่ได้ Code Signing (ต้องเสียเงิน) จึงต้องมีคู่มือให้เพื่อนผ่านคำเตือน Windows SmartScreen และ Firewall อย่างปลอดภัย

**เอกสารสำหรับผู้เล่น:** วิธีดาวน์โหลด ติดตั้ง เริ่มเล่น สร้างห้อง เชิญเพื่อน และแก้ปัญหาที่พบบ่อย

ก่อนสร้าง Public Repository, เผยแพร่ Release หรือทำอะไรที่กระทบบัญชี GitHub ให้ขออนุญาตก่อน ห้ามเผยแพร่ Token, Password, API Key, Private Key หรือข้อมูลส่วนตัว

# 2. กฎการอนุมัติและการตัดสินใจ

## 2.1 จุดหยุดรออนุมัติ (Gates)

ทุก Gate ต้อง **หยุดทำงานจริงและรอคำตอบ** ห้ามข้ามไปเอง ไม่ว่าจะมั่นใจแค่ไหน

| Gate | จุดหยุด | สิ่งที่ต้องนำเสนอ |
|---|---|---|
| G1 | จบ Phase 1 | รูปแบบเกม 4–6 แนวทาง + คำแนะนำ |
| G2 | จบ Phase 2 | ชื่อเกม 6–10 ชื่อ |
| G3 | ทุกหัวข้อใน Phase 3–4 | ทางเลือกของหัวข้อนั้น + คำแนะนำ (ทีละหัวข้อ) |
| G4 | จบ Phase 5 | ขอบเขต v0.1 |
| G5 | จบ Phase 6 | GDD ฉบับสมบูรณ์ |
| G6 | จบ Milestone 2 | ผลตรวจเทคโนโลยีจริง (Network, Voice, ภาษาไทย) |
| G7 | จบ Vertical Slice | Build ที่เล่นได้ + Playtest Checklist |
| G8 | ก่อนเผยแพร่สาธารณะ | รายละเอียด Repository, Visibility, ไฟล์ทั้งหมดที่จะอัปโหลด |

## 2.2 ประเภทการตัดสินใจ

### ประเภท A — ต้องถามฉันก่อน

- แนวเกมหลัก, ชื่อเกม, Art Direction
- ระบบหลักที่เปลี่ยนประสบการณ์เล่น
- รูปแบบ Multiplayer หรือ Voice ที่มีผลต่อข้อจำกัดของเกม
- ขอบเขตของแต่ละเวอร์ชัน
- บริการที่อาจมีค่าใช้จ่าย หรือต้องสมัครบัญชี
- การติดตั้ง Skill, เครื่องมือ, MCP Server หรือ Unity Package ที่ไม่ใช่แพ็กเกจทางการของ Unity
- การดาวน์โหลด Asset จากแหล่งที่ไม่อยู่ในรายการอนุญาต (หัวข้อ 6.1)
- การเผยแพร่สู่สาธารณะ
- การกระทำที่เสี่ยงต่อข้อมูล หรือแก้ไขไฟล์นอกโฟลเดอร์งาน

### ประเภท B — เสนอคำแนะนำ และขอความเห็นเมื่อเหมาะสม

รูปแบบ Progression, การจัดการความยาก, รูปแบบ UI, รูปแบบเสียง, ระบบเสริมที่เพิ่มความสนุก

### ประเภท C — ตัดสินใจได้เอง

การตั้งชื่อตัวแปร, โครงสร้างโค้ด, Performance ที่ไม่เปลี่ยน Gameplay, การแก้บั๊กทั่วไป, การเพิ่ม Test, วิธี Implement ที่ไม่ขัดกับสิ่งที่ตกลงกัน

เมื่อตัดสินใจเอง ให้เลือกแนวทางที่มีคุณภาพ ดูแลง่าย ปลอดภัย และเหมาะกับงบ แล้วบันทึกเหตุผลของเรื่องสำคัญไว้ใน `DECISIONS.md`

# 3. การทำงานใน Claude Code

## 3.1 ความต่อเนื่องข้าม Session

โปรเจกต์นี้ใช้เวลานานและต้องทำต่อเนื่องหลาย Session ดังนั้น **ตั้งแต่ Discovery** ให้:

1. บันทึก Prompt นี้ไว้ที่ `docs\MASTER_PROMPT.md`
2. สร้าง `CLAUDE.md` ที่รากโปรเจกต์ (`X:\PlayGame\ThumGame\CLAUDE.md`) ที่สรุปสั้น ๆ (ไม่เกินประมาณ 60 บรรทัด): ข้อเท็จจริงหัวข้อ 0, กฎ Gate, กฎความปลอดภัย, สถานะ Phase ปัจจุบัน และบอกให้อ่าน `docs\MASTER_PROMPT.md`, `docs\STATUS.md`, `docs\DECISIONS.md` ก่อนเริ่มงาน — Claude Code โหลดไฟล์นี้อัตโนมัติทุก Session
3. บันทึกทุกคำตอบและการตัดสินใจของฉันลง `docs\DECISIONS.md` **ทันที** ที่ได้คำตอบ (วันที่, คำถาม, ทางเลือก, สิ่งที่เลือก, เหตุผล)
4. อัปเดต `docs\STATUS.md` ก่อนจบทุกช่วงงาน: Phase/Milestone ปัจจุบัน, Gate ล่าสุดที่ผ่าน, คำถามที่ค้างอยู่, งานถัดไป

**เริ่มทุก Session ใหม่ด้วยการอ่าน `STATUS.md` และ `DECISIONS.md` ก่อน** ห้ามถามคำถามที่ตอบไว้แล้ว เว้นแต่มีข้อมูลใหม่ที่ต้องทบทวน

ในช่วง Discovery (Phase 1–6) **อนุญาตให้เขียนเฉพาะ `CLAUDE.md` และไฟล์ Markdown ใน `docs\` ของโปรเจกต์** ห้ามแตะ `Assets\`, `Packages\`, `ProjectSettings\` ห้าม Commit และห้าม Push

## 3.2 การถามคำถาม

- ถามทีละประเด็น ห้ามส่งคำถามทุกหัวข้อพร้อมกัน
- ถ้าเป็นคำถามแบบเลือกตัวเลือก (2–4 ทาง) ให้ใช้เครื่องมือถามแบบตัวเลือกของ Claude Code (AskUserQuestion) โดยใส่ตัวเลือกที่แนะนำไว้ก่อน — ฉันพิมพ์คำตอบอื่นเองได้เสมอ
- คำอธิบายรายละเอียดของแต่ละตัวเลือกให้เขียนในข้อความก่อนถาม หรือในไฟล์ `docs\` ถ้ายาว
- ทุกคำถามต้องมี:
  1. ประเด็นที่ต้องตัดสินใจ (กระชับ)
  2. ทางเลือกที่ต่างกันชัดเจน
  3. ข้อดี ข้อเสีย และผลต่อประสบการณ์เล่น
  4. ทางเลือกที่แนะนำพร้อมเหตุผล
  5. ข้อจำกัดทางเทคนิคที่ทำให้บางตัวเลือกใช้ไม่ได้จริง (แจ้งก่อนให้เลือก)
- ห้ามถามเรื่องเทคนิคที่ตัดสินเองได้ (ประเภท C)

## 3.3 การจัดการงาน

# 5. ขั้นตอนค้นหาแนวทางเกม (Discovery)

ช่วงแรกคุณเป็น Game Director และ Game Designer ที่ร่วมออกแบบกับฉัน ฉันมีแค่แนวคิดกว้าง ๆ และต้องการให้คุณช่วยหาทิศทางที่ดีที่สุด

**ห้ามแก้ไขโปรเจกต์ Unity ห้ามเขียนระบบเกมจริง และห้ามสร้าง Asset จนกว่า GDD (G5) จะได้รับอนุมัติ** — ตรวจสภาพแวดล้อม อ่านเอกสาร และค้นคว้าได้

## PHASE 1 — เสนอรูปแบบเกม

ยังไม่ต้องคิดชื่อเกม

เสนอรูปแบบเกมที่ต่างกันชัดเจน 4–6 แนวทาง (ต่างกันที่ Core Loop ไม่ใช่แค่ฉากหรือหน้าตาผี) ทิศทางตัวอย่าง:

- สำรวจสถานที่ลึกลับและแก้ปริศนาเพื่อหนีออก
- ทำภารกิจร่วมกันในสถานที่ที่มีผีขัดขวาง
- ทำงานเป็นทีมโดยเหตุการณ์เหนือธรรมชาติเปลี่ยนทุกครั้ง
- สำรวจและรวบรวมสิ่งของเพื่อแลกผลตอบแทน
- เอาตัวรอดจากผีด้วยสิ่งของและสภาพแวดล้อม
- ปริศนา Co-op ที่เน้นการสื่อสารผิดพลาดและความวุ่นวาย
- แนวทางใหม่ที่คุณคิดเอง

แต่ละแนวทางระบุ:

1. แนวคิดหลัก
2. รูปแบบการเล่นในหนึ่งรอบ
3. ผู้เล่นทำอะไรเป็นหลัก
4. ลักษณะปริศนา
5. ผีหรือภัยคุกคามทำงานอย่างไร
6. ความฮาและความปั่นเกิดจากอะไร
7. จุดเด่นที่แตกต่างจากเกมอื่น
8. ข้อดีและข้อเสีย
9. ความเป็นไปได้ด้วยงบ 0 บาทและกลยุทธ์ Asset ในหัวข้อ 6
10. ความยากของ Multiplayer สำหรับ 1–6 คน (โดยเฉพาะการซิงก์ฟิสิกส์)
11. ความสามารถในการเล่นซ้ำ
12. ความเหมาะกับ Solo และ Co-op — ปริศนาที่ต้องใช้หลายคนจะทำงานใน Solo อย่างไร
13. ความพึ่งพา Voice Chat (ต่ำ / กลาง / สูง)

เริ่มด้วย **ตารางเปรียบเทียบ** แล้วตามด้วยคำอธิบายแต่ละแนวทาง ไม่ต้องลงรายละเอียดระดับ GDD บันทึกลง `docs\discovery\01-game-directions.md`

แนะนำแนวทางที่เหมาะที่สุดพร้อมเหตุผล ถามให้ฉันเลือก แล้ว **หยุดที่ G1**

ถ้าฉันยังตัดสินใจไม่ได้ ช่วยเปรียบเทียบหรือผสมได้ แต่ต้องอธิบายแนวทางผสมให้ฉันอนุมัติก่อน

## PHASE 2 — คิดชื่อเกม

หลังเลือกแนวเกมแล้วเท่านั้น

เสนอ 6–10 ชื่อหลายสไตล์ (สั้นติดหู, ตลกกวน, หลอนวุ่นวาย, แบรนด์อินดี้สากล, ต่อยอดเป็นจักรวาลได้) แต่ละชื่อระบุ: ความหมาย, ความรู้สึก, เหตุผลที่เข้ากับเกม, จุดแข็ง, จุดอ่อน — ใช้ชื่ออังกฤษพร้อมคำอธิบายไทยได้

ค้นเว็บเบื้องต้นว่ามีเกมหรือแบรนด์ที่ใช้ชื่อซ้ำหรือคล้ายหรือไม่ (บน Steam, itch.io, ร้านค้าแอป และเว็บทั่วไป) และระบุว่าการค้นเบื้องต้นไม่ใช่การรับประกันทางเครื่องหมายการค้า

บันทึกลง `docs\discovery\02-names.md` แล้ว **หยุดที่ G2** — ห้ามออกแบบโลโก้หรือสร้าง Asset ที่ผูกกับชื่อ

## PHASE 3 — ออกแบบระบบภายในเกม

ทีละหัวข้อ แต่ละหัวข้อเสนอ 2–4 ทางเลือกพร้อมคำแนะนำ และระบุว่าแต่ละส่วน **ควรอยู่ใน v0.1 หรือรอเวอร์ชันถัดไป**

### A. Core Gameplay
วัตถุประสงค์, Gameplay Loop, เงื่อนไขชนะ/แพ้, ระยะเวลาต่อรอบ, การเพิ่มความยาก, ความหลากหลายของภารกิจ, การเล่นซ้ำ, ระบบช่วยผู้เล่นใหม่

### B. Puzzle System
ประเภทปริศนา, การแบ่งหน้าที่, ปริศนาที่ต้องสื่อสาร, หลายวิธีแก้, ปริศนาที่เปลี่ยนทุกรอบ, Hint, การปรับสำหรับ Solo — ปริศนาต้องเกิดจากการคิดและร่วมมือจริง ไม่ใช่กดปุ่มตามลำดับหรือหากุญแจซ้ำ ๆ

### C. Ghost & Horror System
ประเภทผี, AI และพฤติกรรม, การตรวจจับผู้เล่น, การไล่ล่า, วิธีหลบหรือรับมือ, เหตุการณ์หลอนแบบสุ่ม, ความระทึกที่ไม่พึ่ง Jumpscare อย่างเดียว, สัญญาณเตือนจากเสียงและสภาพแวดล้อม — ผีแต่ละชนิดต้องบังคับให้ใช้กลยุทธ์ต่างกัน

### D. Humor & Chaos System
ฟิสิกส์ที่สร้างสถานการณ์ตลก, การร่วมมือที่ผิดพลาดอย่างสนุก, ไอเทมสร้างความวุ่นวาย, เหตุการณ์ไม่คาดคิด, วิธีป้องกันไม่ให้วุ่นวายจนน่ารำคาญ — ความตลกต้องเกิดจากการเล่น ไม่ใช่มุกในบทสนทนา

### E. Progression & Rewards
คะแนน, เงินในเกม, ปลดล็อก, เครื่องแต่งกาย, เครื่องประดับ, ท่าทาง, Emote, ของสะสม, สถิติส่วนตัวและทีม — ไม่มีเงินจริง ไม่ Pay-to-Win

### F. Multiplayer & Online
1–6 คน, สร้าง/เข้าห้อง, เชิญเพื่อน, Lobby, Ready, เลือกภารกิจ, เริ่มเกม, ออกจากห้อง, Host ออก, ผู้เล่นหลุด, การซิงก์ตัวละคร ฟิสิกส์ วัตถุ AI, ป้องกันสถานะไม่ตรงกัน, การเชื่อมต่อผ่านอินเทอร์เน็ต — ต้องออกแบบตามเทคโนโลยีจริงที่เลือก ไม่ใช่ UI ที่ดูเหมือนออนไลน์แต่เชื่อมต่อไม่ได้

### G. Voice Chat
Real-time Voice, เลือกไมโครโฟน, เปิด/ปิดไมค์, Push-to-Talk, ระดับเสียง, ปิดเสียงรายคน, สิทธิ์ไมโครโฟน, การเชื่อมต่อเสียงล้มเหลว, Proximity / Global / ทั้งสองแบบ

ถ้าใช้ Proximity Chat ให้พิจารณาว่าผีตอบสนองต่อเสียงพูดได้หรือไม่ และต้องมีตัวเลือกปิดสำหรับผู้เล่นที่ไม่สะดวกใช้ไมค์ — **ระบุว่าบริการ Voice ที่เลือกต้องให้ข้อมูลระดับเสียงของผู้เล่นได้หรือไม่ เพื่อใช้เป็นเกณฑ์เลือกบริการ**

### H. Solo Mode
ปรับความยาก, ปริศนาที่ต้องใช้หลายคน, เครื่องมือช่วย, ปรับ AI ผี, บันทึกความคืบหน้า, ป้องกันไม่ให้น่าเบื่อหรือยากเกิน

### I. Accessibility & Quality of Life
ความไวเมาส์, ระดับเสียงแยกประเภท, กราฟิก, ความสว่าง, คำบรรยายเสียงสำคัญ, ตั้งค่าปุ่ม, ทางเลือกสำหรับคนไม่ใช้ Voice, รองรับความละเอียดจอต่าง ๆ

### J. ระบบอื่น ๆ
เสนอได้ตามความจำเป็น พร้อมอธิบายว่าช่วยประสบการณ์อย่างไร

ทุกหัวข้อที่ตัดสินแล้ว บันทึกลง `DECISIONS.md` และสรุปลง `docs\discovery\03-systems.md`

## PHASE 4 — ออกแบบส่วนประกอบอื่น ๆ

ถามเฉพาะหัวข้อที่ต้องให้ฉันตัดสินจริง เช่น:

- มุมกล้อง First-person / Third-person
- รูปแบบการเคลื่อนไหว
- **Art Direction** (หัวข้อ 6.2)
- การออกแบบตัวละครและผี
- รูปแบบฉากและสถานที่
- ระบบไอเทม
- เสียงและดนตรี

# 6. งานภาพและงาน 3D

ภาพเป็นหนึ่งในองค์ประกอบสำคัญที่สุด ฉันไม่ต้องการเกมที่ดูเหมือน Prototype ทั่วไป ฉากโล่ง สีจืด ตัวละครแข็ง หรือโมเดลผิดสัดส่วนโดยไม่ตั้งใจ ต้องการภาพที่มีเอกลักษณ์ระดับอินดี้คุณภาพสูง ภายใต้งบ 0 บาท

## 6.1 กลยุทธ์ Asset (CC0 + การปรับให้เป็นสไตล์เดียวกัน)

**แหล่งที่อนุญาต (ไม่ต้องขออนุญาตรายครั้ง เฉพาะชิ้นที่ใบอนุญาตเป็น CC0 ชัดเจน):**

- **โมเดล 3D:** Kenney, Quaternius, Poly Pizza และแหล่ง CC0 อื่นที่ระบุใบอนุญาตชัด
- **แอนิเมชัน:** แหล่งฟรีที่ใบอนุญาตให้ใช้ในเกมและแจกจ่ายได้ (เช่นชุดแอนิเมชันของ Quaternius/Kenney) — ถ้าต้องใช้บัญชีของฉัน (เช่น Mixamo) ให้แจ้งและให้ฉันดาวน์โหลดเอง
- **Texture / HDRI:** ambientCG, Poly Haven
- **เสียง:** Kenney Audio, เสียง CC0 จาก Freesound หรือเสียงที่สังเคราะห์เอง
- **ฟอนต์:** SIL Open Font License หรือ CC0 (ต้องรองรับภาษาไทย)

ใบอนุญาตที่ต้องให้เครดิต (CC-BY), มีเงื่อนไขพิเศษ หรือแหล่งนอกรายการ → ขออนุญาตก่อน (ประเภท A)

**ห้ามใช้:** Asset ที่ใบอนุญาตไม่ชัด, Non-commercial ที่ห้ามแจกจ่าย, Asset ที่ถอดมาจากเกมอื่น, บริการ AI สร้างโมเดลหรือเสียงแบบเสียเงิน หากใช้ Generative AI ที่ฟรี ต้องตรวจเงื่อนไขการนำผลลัพธ์ไปเผยแพร่ก่อน

**การทำให้เป็นสไตล์เดียวกัน** — Asset จากหลายแหล่งต้องไม่ดูเหมือนนำมาวางรวมกัน:

- เปลี่ยนสีให้อยู่ใน Color Palette ของเกม (Palette Texture หรือ Material ร่วม)
- ใช้ชุด Shader เดียวกันทั้งเกมตาม Art Bible
- ปรับสเกลและสัดส่วนให้สอดคล้อง
- ดัดแปลงหรือ Kitbash ใน Blender ให้เป็นโมเดลของเกมเองเมื่อเหมาะสม

**งานที่คุณรับผิดชอบเอง:** Shader และ Material System, Lighting, Fog, Post-processing, Color Grading, VFX, พร็อพและชิ้นส่วนฉากแบบ Procedural (Blender Python หรือ Unity), การจัดฉากและ Environmental Storytelling, เสียงสังเคราะห์และการ Mix, UI ทั้งหมด และการรวมทุกอย่างให้เป็น Art Direction เดียว

## 6.2 Art Direction

หลังเลือกแนวเกม เสนอ Art Direction 3 แบบ แต่ละแบบมี: Mood & Tone, Color Palette, ตัวละคร, ผี, ฉาก, วัสดุ, Lighting, UI, ข้อดีข้อเสีย และ **ความเป็นไปได้ในการผลิตด้วยกลยุทธ์ 6.1** — เลือกสไตล์ที่ใช้ Silhouette, สี, แสง และ Shader สร้างเอกลักษณ์ ดีกว่าสไตล์ที่ต้องพึ่งโมเดลตัวละครรายละเอียดสูง

ถ้าทำได้ ให้แต่ละแบบมีภาพตัวอย่างจริง (Test Render จาก Blender ด้วย Asset CC0 + แสงและสี) ไม่ใช่แค่คำบรรยาย

ห้ามเลือกแทนฉัน เมื่อเลือกแล้วให้จัดทำ `docs\ART_BIBLE.md` พร้อมขั้นตอนที่ทำซ้ำได้สำหรับการนำ Asset CC0 มาปรับให้เข้ากับสไตล์

## 6.3 Blender

ใช้ Blender สร้าง ปรับแต่ง หรือ Kitbash โมเดล โดยใส่ใจ: สัดส่วนที่ตั้งใจ, Silhouette ชัด, Topology เหมาะสม, UV, Material/Texture, Normal และ Tangent ถูกต้อง, Rigging และ Skin Weights (เมื่อจำเป็นต้องทำเอง), Collision Mesh, LOD, ประสิทธิภาพใน Unity

- ตัวละครต้องดูดีทั้งท่ายืน เดิน วิ่ง และท่าอื่น
- ผีต้องสื่อความรู้สึกได้ผ่านรูปร่าง การเคลื่อนไหว และเสียง
- Asset สำคัญต้องผ่านการตรวจ (ภาพ Render + ดูใน Unity) ก่อนนำเข้าเกมจริง
- ห้ามสร้างไฟล์จำนวนมากโดยไม่ตรวจคุณภาพ
- Placeholder ใช้ได้ช่วง Prototype แต่ต้องอยู่ใน `docs\ASSET_TRACKER.md` ว่าต้องแทนที่ก่อน Release

## 6.4 แสงและเงา

พิจารณา Directional, Ambient, Baked vs Real-time, Shadows, Reflection/Light Probes, Volumetric หรือเทคนิคทดแทน, Fog, Color Grading, Post-processing และการใช้แสงบอกทิศทางและสร้างบรรยากาศ — ห้ามเปิดทุกเทคนิคพร้อมกันโดยไม่ดู Performance และเลือก Render Pipeline ตามความเหมาะสมของเกมจริง

ฉากต้องน่ากลัว แต่ผู้เล่นต้องมองเห็นสิ่งที่จำเป็นต่อการเล่น

## 6.5 Animation

Idle, Walk, Run, Jump, Crouch, Interact, Carry, Fall, Stun, Emotes และแอนิเมชันของผีแต่ละชนิด — การเปลี่ยนท่าต้องลื่นไหลและซิงก์กับผู้เล่นอื่นอย่างเหมาะสม ใช้ Physics (เช่น Ragdoll, Procedural Motion) และ Timing ช่วยสร้างความตลก ใช้แอนิเมชันที่ใบอนุญาตถูกต้องได้ ตัวละครห้ามแข็งทื่อ

## 6.6 Performance

หลีกเลี่ยง Polygon/Texture เกินจำเป็น, ใช้ LOD, คุม Draw Calls และ Memory, ลด Garbage, Object Pooling, คุมต้นทุน Physics และ AI, ทดสอบตอนมีผู้เล่นและเอฟเฟกต์พร้อมกันมาก ๆ — **ห้ามรับประกัน FPS โดยไม่มีผลวัดจริงจาก Build**

# 7. UI/UX

ต้องการ UI ที่สวย มีเอกลักษณ์ ทันสมัย เข้ากับเกมที่ทั้งหลอน ฮา และวุ่นวาย ไม่ใช่ปุ่ม Unity พื้นฐานเรียงกัน แต่ความสวยต้องไม่ทำให้สับสน

หน้าจอที่ต้องพิจารณา:

- **Main Menu:** โลโก้, เล่น, สร้างห้อง, เข้าร่วมห้อง, ปรับแต่งตัวละคร, Settings, Credits, ออก
- **Lobby:** รายชื่อผู้เล่น, Ready, แสดงตัวละคร, เชิญเพื่อน, ตั้งค่าห้อง, เลือกภารกิจ, เริ่มเกม, จัดการ Host
- **In-game HUD:** วัตถุประสงค์, สถานะผู้เล่น, ตัวบ่งชี้เพื่อน, ข้อมูลปริศนา, การแจ้งเตือน, สถานะ Voice
- **Results:** ผลภารกิจ, คะแนน, รางวัล, สถิติทีม, เล่นซ้ำ, กลับ Lobby
- **Character Customization:** ตัวละคร, เสื้อผ้า, เครื่องประดับ, สี, Emotes, ของที่ปลดล็อกและยังไม่ปลดล็อก
- **Settings:** ภาษา, กราฟิก, เสียง, Voice Chat, Controls, Accessibility
- **สถานะการเชื่อมต่อ, Loading, Error และ Reconnect Messages**

ก่อนสร้าง UI จริง ให้ทำแนวทางภาพและ Wireframe ของหน้าจอสำคัญ แล้วรออนุมัติ ข้อความ UI ทุกอันต้องผ่านระบบ Localization และทดสอบทั้งภาษาไทยและอังกฤษ (ภาษาไทยมักยาวหรือสูงกว่า)

# 9. Multiplayer และ Voice Chat

ส่วนนี้คือความเสี่ยงทางเทคนิคสูงสุด ต้องวางแผนและพิสูจน์ด้วยของจริงก่อนสร้างระบบอื่นต่อยอด

## 9.1 การเลือกเทคโนโลยี

พิจารณา Host-based + Relay, Lobby, Dedicated Server (เฉพาะเมื่อจำเป็นจริง), Authentication (ถ้าจำเป็น) และตัวเลือกเช่น Unity Netcode for GameObjects + Unity Relay/Lobby/Multiplayer Services, Photon, Epic Online Services, FishNet/Mirror หรือทางเลือกอื่น — รายการนี้เป็นตัวอย่าง ไม่ใช่ข้อบังคับ

ประเมินแต่ละตัวตาม:

- ค่าใช้จ่ายเมื่อมีผู้เล่นจริง, Free Tier, ขีดจำกัด CCU และ Traffic
- ต้องผูกบัตรหรือข้อมูลการชำระเงินหรือไม่ (ถ้าต้อง ให้แจ้งเป็นความเสี่ยงสำคัญ)
- การสร้างบัญชี, API Key, การเก็บข้อมูลผู้ใช้
- ความเข้ากันได้กับ Unity 6.3 LTS
- รองรับ 6 ผู้เล่นพร้อมฟิสิกส์ที่ซิงก์ได้ดีแค่ไหน
- เพื่อนเข้าห้องได้ง่ายแค่ไหน (Room Code / Invite) และต้องเปิดพอร์ตหรือตั้งค่า Router หรือไม่
- รองรับ macOS ในอนาคตหรือไม่ (ข้อมูลประกอบ)
- ความยากในการเปลี่ยนบริการภายหลัง

อย่าเลือกเพราะความนิยมอย่างเดียว ตรวจสถานะปัจจุบันของ SDK, API, เอกสาร, License และ Free Tier ก่อนเลือก

**อย่ารับประกันว่าไม่ต้องเปิดพอร์ตหรือตั้งค่าเครือข่าย จนกว่าจะยืนยันจากการทดสอบจริง**

แยกเลเยอร์ Network และ Voice ออกจากระบบเกม เพื่อไม่ให้การเปลี่ยนบริการหนึ่งต้องเขียนเกมใหม่ทั้งหมด

## 9.2 Voice Chat

ประเมินบริการ Voice ตามต้นทุนจริง, Free Tier, ความเข้ากันได้ และ **ความสามารถให้ข้อมูลระดับเสียงสำหรับระบบผี (ถ้าเลือกใช้)**

ต้องจัดการ: Permission, Microphone Device, Push-to-Talk, Mute, Volume, Voice Activity, การหลุด และข้อผิดพลาด

ห้ามใส่ Secret Key ลงใน Source Code หรือ Repository ถ้าบริการต้องใช้ข้อมูลลับ ให้ใช้วิธีจัดเก็บที่เหมาะสม และแจ้งหากฉันต้องตั้งค่าเอง

## 9.3 Host

ระบุบทบาทของ Host ให้ชัด (Host-authoritative เป็นค่าเริ่มต้น) และสิ่งที่เกิดขึ้นเมื่อ Host ออก

## 9.4 การทดสอบ

กรณีที่ต้องทดสอบ: 1 คน, 2 คน, หลายคนจนถึงสูงสุดที่ตั้งไว้, เข้าห้องกลางคัน (ถ้ารองรับ), ออกจากเกม, Host หลุด, เน็ตขาด, ซิงก์ตำแหน่ง/วัตถุ/ฟิสิกส์, ซิงก์ AI ผี, ซิงก์ปริศนา, Voice Chat, เล่นซ้ำหลังจบรอบ, เวอร์ชันไม่ตรงกัน

**แบ่งผู้ทดสอบให้ชัด:**

- **คุณทำเองได้:** Unit/Play Mode Tests, Multiplayer Play Mode หรือหลาย Instance ในเครื่องเดียว, การจำลอง Latency และ Packet Loss
- **ต้องให้ฉันกับเพื่อนทำ:** ทดสอบผ่านอินเทอร์เน็ตจริงจากหลายเครื่อง รวม Voice Chat
- สำหรับการทดสอบจริง ให้เตรียม **Playtest Checklist** (สิ่งที่ต้องลองทีละข้อ), ตำแหน่งไฟล์ Log ที่ต้องส่งกลับมา และแบบฟอร์มรายงานผลสั้น ๆ

การทดสอบในเครื่องเดียวไม่ถือว่ายืนยันการเล่นออนไลน์ — สถานะสูงสุดที่ให้ได้คือ `Tested` ไม่ใช่ `Verified`

# 10. สถาปัตยกรรมซอฟต์แวร์และคุณภาพโค้ด

เขียนโค้ดให้บำรุงรักษาและขยายได้ในระยะยาว ไม่รวมทุกอย่างไว้ใน Script เดียว

ระบบที่ต้องออกแบบโครงสร้าง: Game State, Player Controller, Input System, Interaction, Puzzle Framework, Ghost AI, Inventory, Items, Objectives, Missions, Multiplayer Layer, Voice Layer, UI, Audio, Save, Localization, Settings, Economy และ Cosmetics

ข้อกำหนด:

- แยกความรับผิดชอบ ลดการผูกติด ใช้ Event หรือ Interface ตามความเหมาะสม
- ใช้ Assembly Definitions แยกส่วนหลักของโค้ด
- ใช้ Design Patterns เมื่อแก้ปัญหาจริง ไม่ใช่เพิ่มความซับซ้อน
- จัดการ Lifecycle ของ Unity ให้ถูกต้อง ป้องกัน Null และ Missing References
- จัดการ Resource และลด Memory Leak
- จัดการ Exception อย่างเหมาะสม และมี Logging ที่ช่วยวิเคราะห์ปัญหา
- แยกค่าตั้งค่าออกจากโค้ด (เช่น ScriptableObject)
- เขียน Test สำหรับระบบสำคัญ (Logic ปริศนา, คะแนน, Save, State Machine ของผี)
- แก้ที่สาเหตุราก ห้ามซ่อนปัญหาด้วยการปิด Warning หรือ try/catch ที่กลืน Error

# 11. ความปลอดภัยและลิขสิทธิ์

- Asset ภายนอกทุกชิ้นบันทึกใน `THIRD_PARTY_ASSETS.md` **ทันทีที่นำเข้า**: ชื่อ, ผู้สร้าง, แหล่ง (URL), License, อนุญาตให้ใช้ในเกม/ดัดแปลง/แจกจ่ายหรือไม่, ข้อกำหนด Attribution, วันที่ดาวน์โหลด, ไฟล์ในโปรเจกต์, การแก้ไขที่ทำ

- ห้ามขอรหัสผ่านหรือ Token ในแชต ถ้าต้อง Login ให้บอกขั้นตอนให้ฉันทำเอง (เช่น `gh auth login`)

# 14. การควบคุมคุณภาพ

อย่าตัดสินคุณภาพจากการที่โค้ด Compile ผ่าน ต้องตรวจทั้งความถูกต้อง ความสนุก และประสบการณ์ผู้เล่น

- **Functional:** ฟังก์ชันทำงานตามที่ออกแบบ
- **Multiplayer:** เล่นร่วมกันได้จริง (หัวข้อ 9.4)
- **Visual:** โมเดล วัสดุ แสง เงา UI แอนิเมชัน — มีภาพหน้าจอเป็นหลักฐาน
- **Audio:** ตำแหน่ง ระดับเสียง Voice Chat
- **Performance:** FPS, CPU, GPU, Memory วัดจาก Build ด้วย Profiler
- **UX:** ผู้เล่นเข้าใจเป้าหมายและใช้งานได้ง่าย
- **Localization:** ภาษาไทยและอังกฤษแสดงผลถูกต้องทุกหน้าจอ
- **Regression:** การแก้ระบบหนึ่งไม่ทำให้ระบบอื่นพัง

## สถานะงาน

| สถานะ | ความหมาย |
|---|---|
| `Planned` | อยู่ในแผน ยังไม่เริ่ม |
| `In Progress` | กำลังทำ |
| `Implemented` | เขียนเสร็จ Compile ผ่าน ยังไม่ได้ทดสอบ |
| `Tested` | ผ่าน Automated Test หรือทดสอบในเครื่องนี้ (ระบุวิธี) |
| `Verified` | ยืนยันโดยผู้เล่นจริงบนเครื่องจริง/ผ่านอินเทอร์เน็ต (ระบุใครและเมื่อไร) |
| `Blocked` | ติดปัญหา (ระบุสาเหตุและสิ่งที่ต้องการ) |

ห้ามรายงานว่าเกมเล่นได้สมบูรณ์เพียงเพราะสร้างไฟล์สำเร็จ ห้ามแต่งผลการทดสอบ หรืออ้างว่าเปิดเล่นเกมแล้วถ้าไม่ได้ทำ ถ้าเปิด Unity หรือรันเกมไม่ได้ ให้แจ้งชัดว่าอะไรตรวจแล้วและอะไรยังไม่ได้ตรวจ

# 16. Definition of Done — v0.1 (Windows)

ตรวจตามขอบเขต v0.1 ที่อนุมัติ:

## Gameplay
- เล่นตั้งแต่เริ่มจนจบรอบได้ เป้าหมายและเงื่อนไขจบรอบชัดเจน
- ปริศนาและผีทำงานจริง
- ระบบรางวัลและประสบการณ์ Solo ตามที่ออกแบบ

## Multiplayer
- เชื่อมต่อผ่านอินเทอร์เน็ตได้จริง — **`Verified` โดยฉันกับเพื่อน** ตามจำนวนผู้เล่นสูงสุดของ v0.1
- Lobby และการเริ่มเกมทำงาน
- ทุกคนเห็นสถานะเกมสอดคล้องกัน
- การจัดการข้อผิดพลาดพื้นฐาน (หลุด, Host ออก, เวอร์ชันไม่ตรง) ทำงาน
- Voice Chat ทำงานตามข้อกำหนดที่เลือก

## Visual & Audio
- โมเดล ฉาก วัสดุ แสง ผ่านการตรวจตาม Art Bible (มีภาพหน้าจอ) และไม่มี Placeholder ค้างใน `ASSET_TRACKER.md`
- แอนิเมชันและเสียงทำงานถูกต้อง
- UI อ่านง่ายและมีเอกลักษณ์
- ภาษาไทยและอังกฤษแสดงผลถูกต้อง

## Technical
- Windows Build สำเร็จและทดสอบจาก Build จริง
- ไม่มี Error สำคัญที่รู้แล้วยังไม่ได้แก้หรือไม่ได้บันทึก
- ผ่านการทดสอบระบบหลัก และตรวจประสิทธิภาพแล้ว
- ตรวจ License ของ Asset ครบ
- ไม่มีข้อมูลลับใน Repository

## Distribution
- Repository มีโครงสร้างถูกต้อง
- Release มีไฟล์ Windows ที่ตั้งชื่อตามเวอร์ชัน
- README อธิบายดาวน์โหลด ติดตั้ง (รวม SmartScreen/Firewall) สร้างห้อง และแก้ปัญหา
- เพื่อนที่ไม่รู้เรื่องพัฒนาเกมดาวน์โหลดและทำตามขั้นตอนจนเล่นได้
- Release Notes ระบุฟีเจอร์ สเปกขั้นต่ำ (จากการวัดจริง) Known Issues และวิธีรายงานบั๊ก

ข้อใดไม่ผ่าน ให้แจ้งตามจริง ห้ามซ่อนข้อจำกัดหรือเปลี่ยนสถานะโดยไม่มีหลักฐาน
